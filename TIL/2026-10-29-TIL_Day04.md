## 학습 내용 : Git 브랜치 병합(Merge)과 팀 프로젝트 협업 실습


오전에는 브랜치를 생성하고 정상적으로 병합되는 경우와 충돌이 발생하는 경우를 실습했다.

오후에는 팀원들과 팀장, 팀원 역할을 번갈아 맡으며 하나의 GitHub 레포지토리를 공유하고 협업하는 과정을 실습했다.

### 오늘 사용한 명령어

브랜치 생성 및 병합

`git checkout -b 브랜치명` : 새로운 브랜치를 생성하고 해당 브랜치로 이동

`git switch main` : main 브랜치로 이동

`git log --oneline` : 커밋 기록을 한 줄로 간략하게 표시

`git log --oneline` --all --graph : 여러 브랜치의 분기 및 병합 관계를 그래프로 표시

`git merge 브랜치명` : 지정한 브랜치의 변경 사항을 현재 브랜치에 병합


GitHub 협업

`git clone URL` : 원격 레포지토리를 로컬에 복제하고 연결

`git remote add origin URL` : 기존 로컬 저장소에 원격 레포지토리 등록

`git remote -v` : 연결된 원격 레포지토리 주소 확인

`git status` : 현재 브랜치 및 파일 변경 상태 확인

`git add` . : 변경 사항을 스테이징

`git commit -m "메시지"` : 스테이징된 변경 사항을 커밋

`git pull origin main` : 원격 main의 변경 사항을 가져와 현재 브랜치에 통합

`git push origin 브랜치명` : 로컬 브랜치의 커밋을 원격 레포지토리에 업로드

## 오늘 실수or 헷갈렸던 부분

### 실수
- .md 파일을 저장하지 않고 커밋 후 푸쉬를 해서 데이터가 업데이트 되지 않았다. 업데이트 되지 않은 파일을 `git pull`로 받은 팀원들이 업데이트 되지 않은 데이터에 작업을 해서 내가 저장 후 새로 `push`한 데이터를 가지고 이후 작업을 실행했다. `ctrl+s`를 습관화하자.

- `README.md`로 올려야 하는 부분을 `REAMM.md` 로 잘못 올렸다. 이때 `commit`까지 진행했을 때와 `push`까지 진행했을때 각각의 해결 방법에 대해 배웠다.

```
`commit`까지 진행한 경우 : `git log --oneline` 으로 커밋 해시 확인 후 `git reset --soft` 를 이용해서 원하는 부분으로 이동한 뒤 내용을 수정하고 다시 `commit`과 `push`를 진행한다.

`push`까지 진행한 경우 : 기존 커밋을 되돌려 작업하기보다 수정 내용을 새로운 커밋으로 추가하는게 안전하다.
```

- 수정 후 커밋하려고 했지만 다음 메세지가 출력됐다
>nothing to commit, working tree clean

저장을 안해서 발생한 문제였다.

### 헷갈렸던 부분

- 팀장과 팀원으로 각각 실습할 때 로컬과 깃을 처음 연결하는 부분이 헷갈렸다. 사용해야 하는 명령어가 달랐는데 팀장은 `git remote add origin URL` 이었고, 팀원은 이미 팀장이 업로드한 데이터에 접근하는것이기 때문에 `git clone`으로 원격 레포에 있는 데이터를 로컬로 복제해온다. 

- 팀원과 팀장이 작성한 Markdown 내용중에 내용은 같지만 줄 번호가 다른 경우가 있었다. 충돌이 일어났을때 이게 원인인가 싶었지만 줄 번호 자체가 충돌의 원인은 아니었다. Git은 공통 커밋을 기준으로 변경된 내용을 비교하기 때문에, 같은 부분을 수정하게 되면 충돌할 수 있다.
