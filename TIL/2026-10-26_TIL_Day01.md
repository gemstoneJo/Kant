## 1. CLI와 현재 작업 위치

**CLI(Command-Line Interface)**는 명령어를 입력해 컴퓨터를 조작하는 방식이다. 오늘 사용한 Git Bash는 Windows에서 Bash 명령을 사용할 수 있게 해준다. 터미널 프롬프트의 `~`는 일반적으로 현재 사용자의 홈 디렉터리이고, `UCRT64`는 Git for Windows의 실행 환경 표기다.

| 명령어/표기 | 설명 | 오늘의 활용 |
|---|---|---|
| `whoami` | 현재 사용자 이름 표시 | 내 사용자 확인 |
| `pwd` | 현재 작업 디렉터리 절대경로 출력 | 어디에서 작업 중인지 확인 |
| `ls` | 현재 디렉터리 항목 출력 | 파일·폴더 확인 |
| `ls -al` | 숨김 항목 포함 상세 목록 출력 | 권한·날짜 등 확인 |
| `ls -alh` | 상세 목록의 크기를 읽기 쉬운 단위로 표시 | `3.0M`처럼 확인 |
| `clear` | 화면의 터미널 출력 지우기 | 화면 정리 |
| `mkdir kant` | `kant` 디렉터리 생성 | 실습 폴더 생성 |
| `cd kant` | `kant` 디렉터리로 이동 | 실습 폴더 진입 |
| `cd ..` | 한 단계 상위 디렉터리로 이동 | 실습 폴더에서 나옴 |
| `cd ~` | 홈 디렉터리로 이동 | 추가로 배운 이동법 |
| `cd -` | 바로 이전 작업 디렉터리로 이동 | 추가로 배운 이동법 |

### 경로 기호

- `.` : 현재 디렉터리
- `..` : 상위 디렉터리
- `~` : 홈 디렉터리
- `/` : 루트 디렉터리 (Git Bash의 `/`는 Windows의 `C:\`와 동일한 개념으로 단정하면 안 됨)

### `ls -alh` 출력 읽기

```bash
# 예: 내 홈 디렉터리의 Desktop 항목
drwxr-xr-x 1 wj952 197609 0 ... Desktop/

# 예: 다른 경로를 가리키는 심볼릭 링크
lrwxrwxrwx 1 wj952 197609 30 ... 'Application Data' -> /c/Users/wj952/AppData/Roaming/

# 예: 일반 파일
-rw-r--r-- 1 wj952 197609 3.0M ... NTUSER.DAT
```

- 첫 문자 `d`는 디렉터리(directory), `l`은 심볼릭 링크(link), `-`는 일반 파일이다.
- 다음 아홉 문자는 세 묶음의 접근 권한을 뜻한다: **소유자 / 그룹 / 기타 사용자**.
- `r`은 읽기(read), `w`는 쓰기(write), `x`는 실행 또는 디렉터리 접근(search/execute), `-`는 해당 권한 없음이다.
- `-a`(all): `.`으로 시작하는 숨김 항목까지 표시한다.
- `-l`(long): 자세한 정보를 표시한다.
- `-h`(human-readable): 크기를 K/M/G 등으로 보기 쉽게 표시한다. `-h`는 주로 `-l`과 함께 쓴다.
- Windows의 Git Bash 권한 표시는 Linux 파일 시스템 권한과 완전히 동일하게 동작하지 않을 수 있다.

**주의:** `ls -alh`에서 파일 옆의 숫자는 파일 크기이지만, 디렉터리의 숫자는 폴더 안의 모든 파일 크기를 합친 총용량이 아니다. 폴더 총용량은 `du -sh 폴더명`으로 확인할 수 있다.

## 2. 터미널 단축키와 명령어 기록

| 입력 | 의미 | 기억할 점 |
|---|---|---|
| `Ctrl + U` | 커서부터 줄의 시작까지 삭제 | 커서가 끝이면 입력 줄 전체를 지운 것처럼 보임 |
| `Ctrl + W` | 커서 앞의 단어(공백 기준 단위) 삭제 | 긴 경로 수정에 유용 |
| `Tab` | 명령어·파일명·경로 자동완성 | 후보가 여러 개면 추가 입력 필요 |
| `↑` / `↓` | 명령어 이력 탐색 | 재입력 시간 절약 |
| `Ctrl + R` | 명령어 이력 역방향 검색 | 예전에 쓴 긴 명령어 찾기 |
| `history` | 현재 셸이 알고 있는 명령어 이력 출력 | 오늘 실습 복기 |
| `history 10` | 최근 이력 10개 표시 | 전체 이력이 길 때 |
| `!!` | 바로 직전 명령어 다시 실행 | 삭제/수정 명령 재실행 주의 |
| `!10` | 이력 10번 명령 재실행 | 이력 번호가 현재 세션 기준으로 달라질 수 있음 |
| `history \| grep cd` | 이력 중 `cd`가 있는 행만 출력 | 파이프(`\|`)로 결과 전달 |

> `history` 번호는 세션이나 설정에 따라 달라질 수 있다. 실제 명령어를 다시 실행하는 `!!`, `!번호`는 신중히 사용한다.

## 3. 텍스트 출력과 파일 작업

### 3-1. `echo`로 터미널에 출력

```bash
echo HelloWorld
# HelloWorld

echo $SHELL
# 현재 환경에 설정된 셸 경로(환경변수 값)를 출력
```

`$SHELL`은 셸 관련 환경변수를 확장해 출력한다. 반드시 **현재 실행 중인 프로세스**의 셸을 정확히 식별하는 명령은 아니다.

### 3-2. `>`와 `>>` — 리다이렉션

```bash
# 파일이 없으면 생성, 있으면 기존 내용을 덮어씀
echo "Hello World" > README.md

# 파일 내용을 읽어서 터미널에 표시
cat README.md

# 파일 끝에 새 내용 추가
echo "Welcome to KANT" >> README.md

# 최종 내용 확인
cat README.md
```

**최종 `README.md` 내용**

```text
Hello World
Welcome to KANT
```

| 기호 | 동작 | 주의 |
|---|---|---|
| `>` | 명령의 표준 출력을 파일에 쓰며 기존 내용 덮어쓰기 | 실수로 원래 파일을 지울 수 있음 |
| `>>` | 명령의 표준 출력을 파일 끝에 추가하기 | 기존 내용 유지 |
| `cat 파일명` | 파일의 내용 출력 | 텍스트 파일 확인에 적합 |

기본 `echo`는 일반적으로 출력 끝에 줄바꿈을 넣으므로 두 메시지가 서로 다른 줄로 저장된다.

### 3-3. VS Code로 열기

```bash
cd kant
code .
```

`code`는 VS Code 실행 명령이며, `.`은 **현재 디렉터리**를 뜻한다. 즉, 현재 `kant` 폴더를 VS Code에서 여는 것이다. (VS Code 명령이 PATH에 등록되어 있어야 사용 가능.)

## 4. 오늘의 실제 터미널 실습 흐름

다음은 사용자가 공유한 기록을 학습 순서로 재배열한 것이다. `history` 번호는 실습 중 기록이 새로 시작되어 서로 다른 로그를 합쳐 기재했다.

```bash
whoami
pwd
ls
clear
ls -al
ls -alh
mkdir kant
cd kant
pwd
ls -al
cd ..
history

cd kant
code .
echo HelloWorld
echo $SHELL
echo "Hello World" > README.md
ls -al
history
cat README.md
echo "Welcome to KANT" >> README.md
cat README.md
history
```

**작은 실수에서 배운 점:** `la -alh`라고 입력했던 것은 `ls -alh`의 오타였고, 바로 고쳐 실행했다. 익숙하지 않은 명령어는 `history`로 다시 확인하면 좋다.

### 내 방식으로 설명하기

처음에는 홈 디렉터리에서 위치와 파일 목록을 확인했다. `kant` 폴더를 새로 만든 뒤 그 안으로 들어가고, VS Code에서 같은 폴더를 열었다. 이후 `echo`와 리다이렉션을 사용해 `README.md`를 만들고, `cat`으로 내용을 확인했다. 마지막으로 `>>`를 이용해 기존 내용을 보존하면서 두 번째 줄을 추가했다.

## 5. 버전 관리의 목적과 도구 비교 (개념 학습)

버전 관리 시스템(VCS)은 **파일 변경 이력을 남겨 과거 상태를 추적·복구하고, 여러 사람이 작업을 조율**하는 데 쓰인다.

| 구분 | SVN | Perforce (P4/Helix Core) | Git | GitHub |
|---|---|---|---|---|
| 본질 | 중앙 집중형 VCS | 중앙 집중형 중심 VCS | 분산형 VCS | Git 원격 저장소 호스팅·협업 플랫폼 |
| 주된 활용 | 사내 프로젝트 협업 | 게임·애니메이션·VFX의 큰 바이너리 에셋 | 소스코드 변경 이력과 분기·병합 | 코드 저장·공유·PR·리뷰 |
| 로컬 Commit | 보통 서버 반영 | Submit으로 서버에 반영 | 로컬 저장소에 기록 | Git 자체 Commit을 호스팅 |
| 특징 | Update / Commit | Sync / Checkout / Submit | Add / Commit / Push / Pull | 저장소·Issue·Pull Request |

### 내가 익숙한 SVN/Perforce와 비교

- **SVN:** `Update`로 서버 변경을 받고, `Commit`으로 서버에 기록한다.
- **Perforce:** `Sync`로 최신 파일을 받고, 필요한 파일을 체크아웃한 뒤 `Submit`한다. 대용량 바이너리 에셋과 잠금 워크플로에 적합하다.
- **Git:** 변경 파일을 `add`로 스테이징하고, `commit`으로 **내 컴퓨터에 이력을 기록**한다. GitHub 등에 올리려면 `push`가 필요하다.

> Git과 GitHub는 다르다. **Git = 버전 관리 도구**, **GitHub = Git 저장소를 온라인에서 공유하는 서비스**다.

### 개념 예시: Git 기본 흐름

```bash
# 아래 코드는 '오늘 직접 실행한 기록'이 아닌 추후 실습용 예시

git status              # 변경 사항 상태 확인
git add README.md       # 특정 파일 스테이징
git commit -m "Add study notes"  # 로컬 변경 이력 생성
git push                # 연결된 원격 저장소로 전송
```

`git push`는 원격 저장소 설정과 적절한 브랜치/권한이 준비되어 있어야 성공한다.

## 6. Branch와 Merge (개념 학습)

**Branch(브랜치)**는 Git의 **별도 개발 이력을 가리키는 포인터**다. 기존 작업을 기준으로 다른 기능을 독립적으로 개발한 뒤 합칠 수 있다. 단순히 폴더를 복사하는 것과는 다르다.

```text
A──B──C──────────F    main
     \           /
      D─────────E     feature/rag
```

- `main`: 안정적인 기준 작업
- `feature/rag`: RAG 기능 개발 작업
- `merge`: 브랜치의 변경 이력을 합치는 작업
- **Merge 전에는** 기능 브랜치의 변경이 `main`에 자동 반영되지 않는다.
- 같은 부분을 서로 다르게 수정하면 **Merge Conflict(병합 충돌)**를 직접 해결해야 할 수 있다.

```bash
# 개념 예시
git switch -c feature/rag  # 브랜치 생성 및 이동
# ... 파일 수정 후 add/commit ...
git switch main           # main으로 이동
git merge feature/rag     # 기능 브랜치 병합
```

**연결되는 실무 상황:** AI Agent를 만들 때 `feature/chatbot`, `feature/rag`, `fix/login`처럼 작업 목적별 브랜치를 만들면 기능 테스트 및 코드 검토가 용이하다.

## 7. Revert vs Reset (개념 학습)

| 구분 | `git revert` | `git reset` |
|---|---|---|
| 핵심 | 특정 Commit의 변경을 **되돌리는 새 Commit** 생성 | 현재 브랜치의 포인터를 **다른 Commit으로 이동** |
| 기존 공유 이력 | 유지 | 브랜치 기록이 달라질 수 있음 |
| 권장 상황 | 이미 Push한 변경을 안전하게 취소 | 아직 공유하지 않은 로컬 Commit 정리 |

### Revert — 기록을 남기며 취소

```text
A → B → C(문제 발생) → D(C의 변경 취소)
```

```bash
git revert HEAD
```

### Reset — 브랜치 기준점을 이동

```text
A → B → C    에서    A → B   (브랜치가 B를 가리킴)
```

```bash
git reset --soft HEAD~1   # Commit만 되돌리고 변경 내용을 스테이징에 유지
git reset --mixed HEAD~1  # Commit과 스테이징을 되돌리고 작업 파일은 유지
git reset --hard HEAD~1   # 해당 Commit 상태로 인덱스와 작업 파일까지 되돌림
```

**특별 주의:** `--hard`는 아직 저장하지 않은 추적 파일 변경을 잃게 할 수 있다. 공유한 브랜치에 `reset`을 적용하면 동료의 이력과 충돌할 수 있으므로 신중해야 한다. 이전 Commit이 즉시 물리적으로 삭제된다는 뜻은 아니며, 일부 상황에서는 `git reflog`로 복구할 수 있다.

## 8. 오늘 헷갈리기 쉬웠던 부분 8개

1. `.`은 현재 디렉터리, `..`는 상위 디렉터리다.
2. `ls -alh`의 맨 앞 `d`/`l`/`-`는 **파일 종류**, 그 뒤의 `rwx`는 **권한**이다.
3. `ls -alh`에서 디렉터리의 크기 표시는 디렉터리 내부 파일 전체 용량과 다르다.
4. `Ctrl + U`는 **커서 앞**을 지우며, 언제나 모든 글자를 지우는 것은 아니다.
5. `>`는 덮어쓰기, `>>`는 추가 쓰기다.
6. `code .`의 `.`은 **현재 폴더**다.
7. Git의 `commit`은 로컬 기록, `push`는 원격 저장소로 전송이다.
8. `revert`는 취소 이력을 **추가**, `reset`은 브랜치의 기준 위치를 **변경**한다.
