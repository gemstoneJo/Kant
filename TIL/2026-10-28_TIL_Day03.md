## 1. 오늘 수업의 전체 흐름

1. `git init`으로 Git 저장소 생성
2. `README.md` 수정 → `git add .` → `git commit`으로 변경 이력 기록
3. `.gitignore`로 임시 파일과 로그 폴더 제외
4. `git remote`로 GitHub 연결 → `git push origin main`
5. 기존 로컬 폴더를 지운 뒤 `git clone`으로 저장소 복제
6. `git reset`의 `--soft`, `--mixed`, `--hard` 비교
7. `git reflog`를 이용해 이전 커밋 다시 찾기
8. `feature/login` 브랜치 생성 및 작업
9. `git merge feature/login`으로 `main`에 병합
10. `git push origin main` 후 작업 브랜치 정리

**핵심 흐름:** 작업 파일 수정 → **스테이징** → **로컬 커밋** → **GitHub 업로드**

| 영역 | 의미 | 관련 명령어 |
|---|---|---|
| Working Tree | 실제 파일을 수정하는 곳 | `git status` |
| Staging Area(Index) | 다음 커밋에 넣을 변경 사항을 준비하는 곳 | `git add .` |
| Local Repository | 내 컴퓨터에 커밋을 기록하는 곳 | `git commit -m "메시지"` |
| Remote Repository | GitHub 등에 커밋을 공유하는 곳 | `git push origin main` |

**주의:** `git commit`과 `git push`는 다르다. 커밋했다고 GitHub에 바로 올라가지는 않는다.

## 2. Git 저장소 초기화

Git은 파일의 변경 이력을 관리하는 버전 관리 시스템이다. `git init`을 실행하면 현재 폴더에 Git 저장소가 만들어지고, 관리 정보를 담는 숨김 디렉터리 `.git`이 생성된다.

### 실행 명령어

- `mkdir kant-study` : `kant-study` 폴더 생성
- `cd kant-study` : 생성한 폴더로 이동
- `git init` : 현재 폴더를 Git 저장소로 초기화
- `ls -al` : `.git` 등 숨김 파일까지 확인
- `git status` : 브랜치와 파일 변경 상태 확인

**헷갈렸던 점:** `git init`은 무조건 `main` 브랜치를 만드는 명령어가 아니라, Git 저장소를 초기화하는 명령어다. 초기 브랜치 이름은 Git 설정에 따라 달라질 수 있다.

## 3. 파일 수정 → Add → Commit → Log

### 실행 명령어

- `echo "# Git Tutorial" > README.md` : `README.md` 파일 작성. `>`는 기존 파일이 있으면 덮어쓰기
- `git add .` : 현재 경로 아래 변경 사항을 스테이징
- `git status` : 스테이징 상태 확인
- `git commit -m "docs : README.md 추가"` : 스테이징된 변경 내용 커밋
- `git log` : 커밋 자세히 조회
- `git log --oneline` : 커밋을 한 줄씩 간략하게 조회
- `git log --oneline --all` : 모든 참조에서 도달할 수 있는 커밋 기록 표시

### 실행 결과 예시: 스테이징 완료

> Changes to be committed:  
> modified: README.md

### 실행 결과 예시: 수정했지만 스테이징 전

> Changes not staged for commit:  
> modified: README.md

### 꼭 구분할 점

- `git add .` : **어떤 변경을 다음 커밋에 담을지 지정**
- `git commit -m "메시지"` : **스테이징된 변경을 로컬 이력으로 저장**
- `git push origin main` : **로컬 커밋을 GitHub에 전송**
- `git add -A` : 저장소 전체 변경 사항을 스테이징. 저장소 루트에서는 일반적으로 `git add .`와 같은 효과
- `git restore README.md` : 스테이징되지 않은 파일 수정 내용 취소. **수정 내용이 사라질 수 있으므로 주의**
- `git restore --staged README.md` : 스테이징만 해제하고 실제 파일 수정 내용은 유지

### 용어

- `HEAD` : 현재 체크아웃한 커밋 위치를 나타내는 Git 참조
- `main` : 기본 작업 브랜치로 많이 쓰는 이름
- `origin/main` : GitHub 원격 `main`의 마지막으로 확인된 위치를 가리키는 원격 추적 브랜치
- `WIP` : Work In Progress(작업 진행 중)

## 4. `.gitignore` — 추적하지 않을 파일 지정

`.gitignore`는 Git이 추적하지 않아도 되는 파일 또는 폴더를 제외하는 설정 파일이다.

### 실행 명령어

- `touch .gitignore` : `.gitignore` 파일 생성
- `touch sample.tmp` : 임시 파일 생성
- `touch temp.dat` : 데이터 파일 생성
- `mkdir Logs` : 로그 폴더 생성
- `git status` : 제외 패턴 적용 확인

### `.gitignore`에 작성한 내용

```gitignore
*.dat
*.tmp
[Ll]ogs
```

- `*.dat` : 이름이 `.dat`으로 끝나는 파일 제외
- `*.tmp` : 이름이 `.tmp`으로 끝나는 파일 제외
- `[Ll]ogs` : `Logs` 또는 `logs`와 일치하는 이름 제외

**주의:** 이미 Git이 추적 중인 파일은 `.gitignore`에 작성해도 자동으로 추적 해제되지 않는다. 특정 폴더만 제외할 때는 `Logs/`와 같은 형식도 사용할 수 있다.

## 5. GitHub 원격 저장소 연결

`origin`은 원격 저장소에 지정한 이름이다. 주로 GitHub 저장소를 `origin`이라는 이름으로 등록한다.

### 실행 명령어

- `git remote -v` : 등록된 원격 저장소 주소 확인
- `git remote add origin https://github.com/gemstoneJo/Kant-study.git` : GitHub 원격 저장소 연결
- `git remote add backup https://github.com/gemstoneJo/Kant-study.git` : 같은 주소를 `backup`이라는 이름으로 추가해 보는 실습
- `git remote remove backup` : `backup` 연결 삭제
- `git push origin main` : 로컬 `main`의 커밋을 GitHub에 업로드

**주의:** `git remote remove backup`은 GitHub 저장소 자체를 삭제하는 것이 아니라 로컬에 등록된 연결 이름만 삭제한다.

## 6. `git clone` — 저장소 다시 내려받기

`git clone`은 원격 저장소의 파일과 Git 이력을 내 컴퓨터에 복제하는 명령어다.

### 실행 명령어

- `cd ..` : 상위 폴더로 이동
- `rm -rf kant-study/` : 로컬 `kant-study` 폴더 강제 삭제 (**매우 주의**)
- `git clone https://github.com/gemstoneJo/Kant-study.git` : GitHub 저장소 복제
- `cd Kant-study` : 복제된 폴더로 이동
- `ls -al` : `.git`, `.gitignore`, `README.md` 등 확인

수업에서는 로컬 폴더를 삭제했다가 GitHub에서 다시 복제했다. **커밋해 원격으로 보낸 파일은 되찾을 수 있지만, 커밋하지 않은 로컬 변경 사항이나 무시된 파일은 `clone`으로 복구되지 않는다.**

## 7. `git reset` — 과거 커밋으로 돌아가기

`git reset`은 현재 브랜치의 커밋 위치를 변경한다. 옵션에 따라 스테이징 영역과 실제 파일도 영향을 받는다.

| 옵션 | 커밋 위치(HEAD) | 스테이징(Index) | 실제 파일(Working Tree) |
|---|---|---|---|
| `--soft` | 대상 커밋으로 이동 | 현재 상태 유지 | 유지 |
| `--mixed` | 대상 커밋으로 이동 | 대상 커밋에 맞게 초기화 | 유지 |
| `--hard` | 대상 커밋으로 이동 | 대상 커밋에 맞게 초기화 | 대상 커밋 상태로 되돌림 |

### 7-1. `--soft`

**실행 명령어:** `git reset --soft fffaaf3`

커밋 위치만 변경하며, 스테이징된 수정 내용은 그대로 남는다.

**실습 후 확인한 상태:**

> Changes to be committed:  
> modified: README.md

### 7-2. `--mixed`

**실행 명령어:** `git reset --mixed fffaaf3`

커밋 위치와 스테이징 영역을 변경하지만 실제 수정 파일은 유지한다. `--mixed`는 `git reset`의 기본 옵션이다.

**실습 후 확인한 상태:**

> Unstaged changes after reset:  
> M README.md

또는 `git status`에서 다음과 같이 확인할 수 있다.

> Changes not staged for commit:  
> modified: README.md

### 7-3. `--hard`

**실행 명령어:** `git reset --hard fffaaf3`

커밋 위치·스테이징·추적 중인 실제 파일을 대상 커밋 상태로 되돌린다.

**실습 결과:**

> HEAD is now at fffaaf3 docs: 깃 초기화 명령어 추가 (WIP)

**경고:** 커밋하지 않은 파일 수정 사항이 사라질 수 있으므로 가장 조심해서 사용한다.

### 외우기

- **Soft** : 커밋만 되돌리기
- **Mixed** : 커밋 + 스테이징 되돌리기
- **Hard** : 커밋 + 스테이징 + 작업 파일까지 되돌리기

**보충:** `git reset --mixed HEAD~1`에서 `HEAD~1`은 현재 커밋의 부모 커밋을 뜻한다. 공유된 커밋을 취소할 때는 이력을 다시 쓰는 `reset`보다 새로운 취소 커밋을 만드는 `git revert`가 더 안전할 수 있다.

## 8. `git reflog` — 잃어버린 것처럼 보이는 커밋 복구

`git log`는 브랜치에서 도달할 수 있는 커밋 기록을 보여준다. 반면 `git reflog`는 HEAD가 이동했던 기록을 확인하는 데 유용하다.

### 실행 명령어

- `git reflog` : HEAD 이동 이력 확인
- `git reset --hard HEAD@{1}` : 현재 Reflog에서 `HEAD@{1}`이 가리키는 커밋으로 이동
- `git log --oneline` : 복구한 커밋 확인

### 실습에서 확인한 이력 예시

> fffaaf3 HEAD@{0}: reset: moving to fffaaf3  
> 68fab22 HEAD@{1}: commit: docs: 커밋 메세지 추가

`git reset --soft fffaaf3`로 돌아간 후 일반 `git log`에서 보이지 않던 `68fab22`를 `git reflog`에서 찾아 복구했다.

**중요:** `HEAD@{1}`, `HEAD@{3}`, `HEAD@{6}` 등의 번호는 실행하는 명령어에 따라 달라진다. **항상 `git reflog`로 현재 번호를 다시 확인**해야 한다. 확실하다면 `git reset --hard 68fab22`처럼 커밋 해시를 직접 지정할 수도 있다.

### 오늘 발생한 오류

- 잘못 입력: `git reset --hard 68fab22 HEAD@{1}`
- 오류 결과:

> fatal: Cannot do hard reset with paths.

대상 커밋 참조를 두 개 지정한 것이 문제였다. **대상 참조는 하나만** 입력한다.

- 잘못 입력: `git log --oneline-all`, `git log --oneline -all`
- 올바른 명령어: `git log --oneline --all`

## 9. `git branch` — 브랜치 생성과 이동

브랜치(Branch)는 다른 작업과 분리해서 개발할 수 있도록 이름을 붙인 작업 흐름이다. 오늘은 `main`과 `feature/login`을 사용했다.

| 실행 명령어 | 기능 |
|---|---|
| `git branch feature/login` | 브랜치 생성만 함 |
| `git branch` | 브랜치 목록 확인 |
| `git branch --list` | 브랜치 목록 확인 |
| `git checkout feature/login` | `feature/login`으로 이동 |
| `git checkout main` | `main`으로 이동 |
| `git checkout -b feature/login` | 브랜치 생성과 이동을 동시에 수행 |
| `git branch --delete feature/login` | 병합 여부 등을 검사하며 안전하게 삭제 |
| `git branch -D feature/login` | 병합 여부 검사 없이 강제 삭제 |

### 브랜치 목록의 별표 `*`

`git branch` 실행 결과:

>   feature/login  
> \* main

별표 `*`는 **현재 사용 중인 브랜치**를 의미한다.

처음 브랜치를 만들었을 때 `main`과 `feature/login`은 모두 같은 커밋 `68fab22`를 가리켰다. 브랜치를 새로 만든다고 파일이 곧바로 달라지는 것은 아니다.

## 10. `git merge` — 브랜치의 작업 내용 병합

`feature/login` 브랜치에서 `README.md`를 수정하고 커밋한 뒤 `main`에 병합했다.

### 실제 실습 순서

1. `git checkout -b feature/login` : 브랜치 생성 및 이동
2. `README.md`에 Git 로그 관련 내용 추가
3. `git status` : 변경 파일 확인
4. `git add .` : 변경 사항 스테이징
5. `git commit -m "docs: Git 로그 명령어 추가"` : 기능 브랜치에서 커밋
6. `git checkout main` : `main` 브랜치로 복귀
7. `git merge feature/login` : `feature/login`의 작업을 `main`으로 병합
8. `git push origin main` : 병합한 결과를 GitHub에 업로드
9. `git branch -D feature/login` : 작업 완료된 로컬 브랜치 삭제
10. `git log --oneline` : 최종 커밋 확인

### 커밋 결과

> [feature/login 3658a45] docs: Git 로그 명령어 추가  
> 1 file changed, 14 insertions(+)

### Merge 결과

> Updating 68fab22..3658a45  
> Fast-forward  
> README.md | 14 ++++++++++++++  
> 1 file changed, 14 insertions(+)

### Fast-forward란?

`main`이 `feature/login`의 이전 커밋을 가리키고 있었으므로, 별도의 병합 커밋을 만들지 않고 `main` 포인터만 새 커밋으로 이동시켰다.

- 병합 전: `main` → `68fab22`, `feature/login` → `3658a45`
- 병합 후: `main` → `3658a45`, `feature/login` → `3658a45`
- Push 후: `origin/main` → `3658a45`

### 최종 `git log --oneline` 결과

> 3658a45 (HEAD -> main, origin/main, origin/HEAD) docs: Git 로그 명령어 추가  
> 68fab22 docs: 커밋 메세지 추가  
> fffaaf3 docs: 깃 초기화 명령어 추가 (WIP)  
> 66c062a docs : Logs 폴더 제외  
> b885067 feat : .gitignore 파일 생성  
> 3ac6bf8 docs : README.md 추가

**의미:** 마지막으로 확인한 로그에서 로컬 `main`과 원격 추적 참조 `origin/main`이 모두 `3658a45`를 가리켰다.

## 11. VS Code의 Markdown 편집 단축키

| 단축키 | 기능 |
|---|---|
| `Alt + ↑` | 현재 줄을 위로 이동 |
| `Alt + ↓` | 현재 줄을 아래로 이동 |
| `Shift + Alt + ↑` | 현재 줄을 위로 복사 |

예를 들어 `git add .`가 있는 줄에서 `Alt + ↓`를 누르면 그 줄이 다음 줄 아래로 **이동**한다. `Shift + Alt + ↓`를 누르면 같은 줄이 아래에 하나 더 **복사**된다.

## 12. 수업에서 나온 기타 명령과 오류

### Bash 이력

- `history` : 이전에 입력한 명령어 목록 확인
- `!24` : `history`에서 24번 명령을 다시 실행 (**실행 전 명령 내용 확인**)

### 잘못 입력한 명령어

| 실수 | 올바른 명령어 | 이유 |
|---|---|---|
| `git add.` | `git add .` | 점 앞 공백 누락 |
| `gis status` | `git status` | 오타 |
| `get reset` | `git reset` | 오타 |
| `git brach -D` | `git branch -D` | 오타 |
| `git log --oneline-all` | `git log --oneline --all` | 옵션 결합 오류 |
| `..` | `cd ..` | 경로만 입력함 |

### 파이프 `|`의 뜻

실습 로그에 등장한 `git add . | git commit -m "..."`는 올바른 일반적인 Add→Commit 흐름이 아니다.

- `|` : 앞 명령의 **표준 출력**을 뒤 명령의 **표준 입력**으로 전달
- Git에서는 `git add .` 실행 후 `git commit -m "..."`을 **별도 명령으로** 실행하는 것이 명확하다.

### LF / CRLF 경고

- `LF` : Unix/Linux 계열에서 많이 쓰는 줄바꿈 방식
- `CRLF` : Windows에서 많이 쓰는 줄바꿈 방식
- `git add .` 중 관련 경고가 나올 수 있으며, 일반적으로 Git의 줄바꿈 처리 설정에 따른 안내로서 커밋 실패를 뜻하지는 않는다.

## 15. 오늘의 회고

### 이해한 내용

- Git의 기본 흐름은 **수정 → Add → Commit → Push**이다.
- `git reset`은 옵션에 따라 작업 파일과 스테이징 영역에 미치는 영향이 다르다.
- `git reflog`는 커밋을 되돌린 뒤 이전 위치를 찾는 데 도움이 된다.
- 브랜치를 나누어 별도로 작업하고 `main`으로 병합할 수 있다.
